# A52s 오프라인 하이브리드 비교

작성일: 2026-11-08. **정확도 비교·A52s 모델 실행 측정·독립 감사 완료.** 사용자가 HGB를 선택하고 별도 설치를 요청하여, 기존 앱·기록을 보존한 채 `SleepWell 오프라인` 0.8.6을 A52s에 설치했다. 인터넷 연결을 끈 실기기 모델 검사 6/6을 통과했다. 설치·보존·모델 검증의 최신 근거는 `install_verification/INSTALL_RESULT_KO.md`와 `a52s_install_verification.json`이다. 아래 준비 단계의 미설치 표현은 사용자 선택 이전의 기록이다.

## 검증 질문과 판단 기준

현재 PC 서버의 TabDPT 하이브리드를 휴대폰에서 실행할 수 있는 후보로 바꿀 때 예측 오차와 자원 사용량이 얼마나 달라지는지 비교한다. 사용자는 허용 오차를 결과를 보고 결정하기로 했다. 따라서 1분 같은 임의의 자동 채택 기준을 적용하지 않는다. 차이가 통계적으로 유의하지 않다는 사실만으로 두 모델이 동등하다고 판단하지도 않는다.

여기서 하이브리드는 수면 기록 특징 33개와 Two-process 계산 특징 6개를 함께 입력하는 방식이다. TabDPT와 HGB 출력을 서로 평균하는 새로운 앙상블을 뜻하지 않는다.

## 공통 평가 설계

현재 배포 모델과 같은 `equal_budget_hybrid9_20261107`의 참여자 분할을 유지한다. CMI는 학습/검증/평가 186/39/44명, MESA는 1,525/299/315명이다. 학습·검증·평가 사이에 같은 사람이 들어가는 경우는 0건이다. 평가 기록은 CMI 673건, MESA 2,175건이다. 과거의 5-fold × 2회 실험은 별개 설계이며 이 표에 합치지 않는다.

기존 Train 전처리와 39개 특징, 출력 제한, 과거 기록만 사용하는 시간순 개인화를 유지한다. 주 지표는 기존 평가와 같은 반감기 14일·수축 강도 14의 잔차 보정 후 입면/기상 절대오차 평균이다. 각 사람 안에서 평균한 뒤 코호트별로 평균하고, CMI와 MESA를 50:50으로 합친다. 보정 전 오차도 따로 보고한다. 이 지표는 앱의 최종 권장 시각 또는 실제 수면 개선 효과의 검증 지표가 아니다.

경량 TabDPT 후보는 검색 문맥 256/512/1,024개 × 앙상블 1/2회의 6개 설정이다. 검증 데이터의 주 지표로 한 설정을 고른 뒤 선택을 기록하고 평가한다. HGB는 기존 검증 데이터에서 이미 선택된 leaf 31 설정을 그대로 사용한다. 전체 문맥·앙상블 4의 현재 TabDPT가 기준이다. 기존 평가자료를 재사용했으므로 새로운 독립 검증이라고 주장하지 않는다.

차이의 불확실성은 코호트 안에서 사람을 짝지어 재표집하는 부트스트랩으로 계산한다. 여러 밤을 서로 독립인 사람처럼 세지 않는다. 신뢰구간은 이 고정 학습자료·모델과 재사용된 평가집단에 조건부인 기술적 결과이며, 재학습·후보 선택·외부 집단의 불확실성 전체를 포함하지 않는다.

## 최종 정확도 비교

서버 없는 A52s 사용에는 HGB를 권고한다. 이 권고는 정확도 우위 때문이 아니라 아래에서 확인한 실행 지연·메모리·파일 크기와의 절충이다. 사용자가 허용 손실을 결과를 보고 정하기로 했으므로 자동 채택 문턱이나 임의의 임상적 허용 기준을 추가하지 않는다. 평균 46초 증가가 모든 사람에게 같은 증가라는 뜻도 아니다. 평가자별 평균 오차의 최대 악화는 HGB에서 CMI 16.34분·MESA 19.18분으로 개인차가 존재했다.

## TabDPT 변환에서 발견한 구현 문제

검색 문맥을 줄이는 native FAISS 방식과 모바일의 거리/행 인덱스 정렬은 중복된 특징 행의 동률을 다르게 처리했다. 일부 입력에서는 선택되는 정답 기록까지 달라졌다. 따라서 모바일은 float32 특징 저장, float64 거리의 특징 순서별 누적, 행 인덱스 동률 규칙을 고정한 별도 구현으로 평가한다.

또한 초기 ONNX 변환은 거의 일정한 문맥 열의 매우 작은 표준편차를 계산할 때 PyTorch와 다른 값을 냈다. 무작위 입력에서는 작던 차이가 실제 입력에서 분 단위 예측 차이로 나타났다. clip/normalize/clip을 명시적인 외부 계산으로 이동했다. 이 계산 변경도 모델의 일부이므로, native 설정의 점수를 그대로 재사용하지 않고 **실제 ONNX 예측의 전체 평가**를 수행한다. 원래의 부정확한 변환을 배포하지 않는다.

전체 Validation을 실행한 뒤에는 더 중요한 변환 오류를 발견했다. encoder-only wrapper가 원본의 학습된 `thinking_embed` 64행과 이에 대응하는 y의 0행, attention 문맥 길이·출력 위치 보정을 누락했다. 또한 원본은 전체 Train y를 정규화한 뒤 이웃을 선택하는데, 최초 변환본은 선택된 이웃의 y를 다시 정규화했다. 두 오류를 수정했다. 잘못된 wrapper를 공유한 PyTorch/ONNX 간 수치 일치는 원본과의 의미 차이를 검출하지 못했다. 초기 모바일 Validation 69.317194분은 **유효한 경량 TabDPT 성능이 아니라 구현 오류가 있는 산출물**로 분리·보존했다. 외부 float64 정규화만이 성능 저하 원인이라고 단정하지 않는다. 수정 구조를 공유 wrapper가 아닌 원본 `model.forward`와 독립 대조한 후 전체 평가를 다시 수행했다. HGB 결과에는 영향이 없다.

수정 v2는 원본의 학습된 64행과 전체 Train y 정규화를 복구했다. 원본 forward와 같은 전처리 tensor를 사용한 독립 구조 비교에서 logit 최대 차이는 0, export용 attention 재표현 후 3.8147e-6이었다. CPU ONNX와 PyTorch의 32개 검증·경계 입력 비교 최대 차이는 0.001724분(약 0.103초), GPU batch16과 CPU 단건 비교 최대 차이는 0.001160분(약 0.070초)이었다. 정렬·전처리까지 원래 구현과 완전히 같다는 뜻은 아니며 실제 v2 전체 출력으로 성능을 평가한다. 동일한 검색·전처리를 맞춘 원본과의 4개 Validation 행 비교는 최대 0.143초 차이였고, 이는 제한적인 진단 결과다.

TabDPT의 가중치는 FP32 약 252MB를 유지하고, 그래프·Train 문맥 등 모델 자산 합계는 약 256.15MB다. 참고 문맥 수와 앙상블 횟수를 줄여 연산량을 낮춘 방식이며, FP16/INT8 양자화 성능은 검증하지 않았다. 수정 v2 전체 Validation MAE는 56.643764분으로, 같은 문맥·앙상블의 native 결과 56.642436분과 가깝다.

6개 native 설정 중 검증 점수가 가장 낮은 문맥 1,024개·앙상블 2회를 선택했다. 검증 MAE는 56.642436분으로 기존 전체 문맥·4회 모델의 56.341805분보다 0.300631분 컸다. 이 수치는 **모바일 변환 전 설정 선택용 결과**이며, 실제 ONNX 모델의 정확도는 별도로 보고한다. 실제 추론 소스·그래프·가중치 해시와 실행 조건도 전체 ONNX 예측을 생성하기 전에 고정했다.

평가자료 접근 범위도 구분한다. 변환 문제를 조사하면서 각 코호트의 정답을 사용하지 않은 Test 특징 64개로 이웃 검색을 점검했고, 첫 Test 특징 1개로 변환 출력을 비교했다. Test 정답이나 오차를 이용한 설정 선택은 하지 않았지만, Test 파일에 전혀 접근하지 않았다고 표현할 수는 없다. 이후 수치 검증은 Validation과 경계 입력으로 수행했다. 기록은 `accuracy/audit_note_test_feature_access.json`에 보존했다.

## 실행 측정의 구분

- 모바일 변환의 수치 일치: 같은 입력에서 Python 기준 예측과 Android/변환 모델의 출력을 대조한다.
- 지연: 모델 로딩, 첫 예측, 준비된 모델의 반복 예측을 구분한다. 모델만의 계산시간과 앱 전체 처리시간도 구분한다.
- 메모리: 파일 크기는 RAM 사용량이 아니다. PSS 등의 시점별 측정과 실제 관찰한 피크를 구분한다.
- 하드웨어: PC GPU, PC CPU, x86 Android 에뮬레이터, A52s ARM 실기기의 결과를 섞어 비교하지 않는다.

USB 디버깅 연결 후 A52s에서 실측했다. 기기는 SM-A528N, Android 14/API 34, arm64이며 OS가 보고한 RAM은 5,489,056KiB(약 5.23GiB)다. 측정 앱은 배포 앱과 다른 패키지를 사용한다.

시간은 준비된 39개 특징으로 CMI·MESA 입면/기상 네 출력을 계산하는 구간이다. 일지에서 특징을 만드는 시간, 개인화, 추천 정책, 화면 갱신은 포함하지 않는다. 메모리는 별도 시험 앱 프로세스에서 관찰한 최대 PSS이며 사용자 앱 전체 메모리나 놓침 없는 절대 피크가 아니다. 모델 파일 크기는 십진 MB, 메모리는 이진 MiB다.

HGB는 200회 예열 후 1,000회를 측정했다. 수정 TabDPT v2는 12개 입력의 제한된 실기기 실행이며 첫 요청을 제외한 11회의 중앙값·p95다. 표본 수와 예열 조건이 달라 엄밀한 속도 비율로 해석하지 않는다. TabDPT p95는 이 작은 표본의 최댓값과 같으며, 느린 요청도 제외하지 않았다. TabDPT 측정 시작/끝의 배터리는 46%/46%, 온도는 30.8/31.4°C, thermal status는 0/1이었다. 화면을 켠 상태로 측정했고 변경했던 충전 중 화면 유지 설정은 복원했다.

Android HGB는 CMI 12개·MESA 12개 golden 입력에서 원본과 최대 차이 0이었다. 수정 Android TabDPT는 CMI Validation에서 선정한 12개 입력 각각을 두 코호트 모델에 넣었으며, 입력 전처리·검색·정규화 hash 불일치는 0, CPU ONNX 기준과 최대 출력 차이는 0.0293초였다. 이 12개 실기기 검사는 MESA 출처 입력·합성 경계까지 모두 검사한 32개 PC 검증과 구분한다. 두 시험 앱에는 인터넷 권한이 없어 해당 추론은 서버 없이 수행됐다. 상세 원자료는 `hgb_android/a52s_final_result.json`과 `tabdpt_android/a52s_corrected_think64_bounded12.json`에 있다.

전체 정확도 평가용 PC 전처리는 Python의 순차 float64 합산을 같은 순서의 NumPy float64 누적으로 옮겼다. 40개 수치 배열과 128개 실제 입력 tensor의 동일성을 검사했고, 별도 검토에서 바이트 단위 불일치가 0이었다. 모바일 예측 알고리즘을 바꾸는 변경이 아니다. 변경 전 소스·고정 기록을 보관했으며 실제 전체 평가 전에 NumPy 버전, 코드 및 그래프 해시를 다시 고정했다. 비교용 수치 일치 기준인 1초는 **모델 채택에 허용하는 예측 오차 증가 기준과 무관하다.**

추가 지연 진단에서는 기존 첫 사례를 포함한 세 입력만 별도로 재실행했다. 예측 wall time은 21.578/24.179/24.024초, process CPU time은 94.230/105.670/104.916초, 전처리·hash 검증은 0.389~1.186초였다. 이전의 173.883초 지연은 같은 입력에서 재현되지 않았으며 원인은 특정하지 못했다. 따라서 초기/최대 지연을 제거하거나 특정 입력·스케줄러·발열 탓으로 단정하지 않는다. 원래 12개 결과는 보존하고 추가 결과를 `tabdpt_android/a52s_variance_probe_cases_0_1_2.json`에 별도로 기록했다.

## 앱 적용 준비 상태(사용자 선택·설치 전 기록)

오프라인 HGB를 연동한 후보 앱을 `E:/sleepwell-builds/offline-hgb-app-candidate-20261108`에 별도로 만들었다. 기존 39개 특징 생성, CMI·MESA 계산, 잔차 보정, 추천 정책을 유지하면서 예측기를 기기 내 HGB로 연결했다. HGB의 실행 경로와 출처는 TabDPT와 구분해 기록한다. 모델을 읽지 못하면 기존 생리 모델의 추천으로 돌아간다. 앱의 CMI·MESA 예측 산술평균 흐름은 유지했지만, 코호트별 평가를 그 산술평균의 검증으로 바꾸어 주장하지 않는다.

컴파일·lint·APK 빌드, 컴파일된 Java 모델의 24개 golden 일치 검사를 통과했다. 별도 패키지 ID의 에뮬레이터 검증 복사본에서 최종 코드 전체 instrumentation 237개가 모두 통과했고, 이 중 HGB 통합 검사는 5개다. 후보 소스 14개 파일과 APK의 hash를 적용 manifest와 독립 대조했고, 교체 대상 정식 소스 6개의 기존 hash가 그대로이며 신규 HGB 파일이 정식 소스에 없음을 확인했다. JVM unit-test task에는 기존 test source가 없어 실행할 테스트가 없었다.

검토용 APK는 `app_candidate_hgb/SleepWell-0.8.6-offline-HGB-candidate-debug.apk`(38,235,880바이트)이며 SHA-256은 `a0e8f54c4ce9f9d91be8fa7c7723b36483193197d287fc9af0e9b126019aab64`다. 이 APK는 정상 앱과 같은 applicationId이므로 아직 사용자 휴대폰에 설치하지 않았다. 정확도와 실행 비용을 확인한 뒤 사용자가 선택하기로 한 조건에 따라, 기존 앱·서버·개인화 상수는 유지했다. A52s에서 검증한 것은 별도 모델 벤치마크 앱이며 완성된 후보 앱 전체의 실기기 검증은 적용 결정 뒤에 남아 있다.

# TabDPT think64 Android 포터블 검증

2026-11-08. 제품 앱과 서버를 변경하지 않고 별도 패키지 `app.sleepwell.tabdptbenchmark`에서 검증했다. 대상은 Validation으로 잠긴 `K=1024`, 앙상블 2개 설정이다.

## 수정된 실행 계약

초기 내보내기에는 두 가지 구조 오류가 있었으므로 해당 APK와 수치는 채택 근거에서 제외했다.

1. 체크포인트의 사전학습 thinking row 64개가 ONNX 래퍼에서 누락됐다.
2. 원 모델은 전체 Train 목표값의 평균·표준편차로 정규화한 뒤 이웃을 선택하지만, 초기 포터블 구현은 선택된 K개 목표값으로 다시 정규화했다.

수정본은 thinking row 64개를 ONNX 내부에 포함하고, 코호트·목표별 전체 Train float32 평균과 표본 표준편차(+`1e-6`)를 manifest에 고정한다. Android는 이 통계로 Train 목표값을 정규화한 뒤 검색된 행을 선택한다. 런타임은 `n_thinking_rows=64`, thinking embedding 해시, 전체 Train 정규화 계약이 없으면 실행을 거부한다.

## 참조 경로 검증

- 원 native forward와 thinking64 래퍼는 attention 교체 전 logits 오차 0이었다.
- 내보내기 가능한 attention과 native 경로의 logits 최대 절대오차는 `3.8147e-6`이었다.
- 독립적으로 정렬한 전체 참조 진단 8개 출력의 중앙값 최대 차이는 `0.002380`분(0.143초)이었다.
- 32개 CPU 기준값에서 ONNX와 PyTorch의 최대 차이는 `0.001724`분이었다.
- CUDA batch 1과 CPU의 최대 차이는 `0.000549`분, CUDA batch 16과 CPU는 CMI `0.001160`분·MESA `0.000488`분이었다.

## Galaxy A52s 실기기 결과

기기는 Samsung SM-A528N, Android 14(API 34), arm64-v8a, 물리 메모리 약 5.24 GiB다. 원시 HYBRID39 한 쌍을 CMI·MESA 전처리와 검색에 통과시켜 입면·기상 4개 출력을 계산하는 모델 전용 구간을 측정했다.

Android에서는 32개 기준값 중 `cmi_validation_uniform_00`~`11`의 12개만 실행했다. 각 raw39는 CMI와 MESA 양쪽 모델을 모두 거친다. 이 제한 실행에는 경계 합성 사례가 없으므로 “Android 32개 전체 통과”로 보고하지 않는다.

| 항목 | 결과 |
|---|---:|
| 전처리·검색·x/y 입력 해시 불일치 | 모두 0건 |
| Android vs Python ONNX 최대 차이 | 0.000488분 (0.029초) |
| Android vs portable PyTorch 최대 차이 | 0.000839분 (0.050초) |
| 콜드 전체 로드 | 8.394초 |
| 첫 4출력 요청 | 173.883초 |
| warm 11회 중앙값 | 22.368초 |
| warm 최소 | 20.985초 |
| warm p95 | 172.361초 |
| 50 ms 표본 최대 PSS | 539,874 KB (527.2 MiB) |

warm p95는 11개 중 최댓값과 같아 작은 표본의 기술값일 뿐 안정적인 모집단 백분위수로 해석하면 안 된다. 실행 전 배터리 46%, 30.8°C, thermal status 0이었고, 종료 후 46%, 31.4°C, status 1이었다. 화면 절전을 막기 위해 USB 연결 중 화면 유지 값을 원래 0에서 2로 일시 변경했으며 종료 후 0으로 복원했다.

느린 첫 요청과 warm 최댓값의 원인을 확인하기 위해 사례 0·1·2만 별도로 재실행했다. 이전에 173.883초였던 같은 사례 0은 21.578초였고 사례 1·2는 24.179초와 24.024초였다. 따라서 느린 관측값이 특정 입력 때문에 발생했다는 증거는 없다. 원인은 현재 자료로 특정할 수 없으며, 기존 173.883초와 172.361초 관측을 버리거나 임의의 스케줄러 문제로 단정하지 않는다.

분산 프로브에서 전처리·해시 검증 단계는 사례별 0.389~1.186초였고, ONNX 예측이 21.578~24.179초로 대부분을 차지했다. 예측 구간의 전체 프로세스 CPU 시간은 94.23~105.67초로, 벽시계 시간 동안 여러 코어를 사용했다. 프로브 전후 thermal status는 모두 0이었다.

## HGB와 운영 비교

동일 A52s의 HGB 모델 전용 결과는 콜드 로드 140.733 ms, 첫 4출력 0.394 ms, warm 1,000회 중앙값 0.072 ms·p95 0.095 ms, 최대 PSS 53.2 MiB였다. 반복 횟수와 내부 계산 구조가 달라 단순 통계 검정 비교는 아니지만, 현재 FP32 TabDPT가 A52s의 즉시 응답형 앱에 비해 지나치게 느리고 약 10배의 PSS를 사용한다는 운영 판단에는 충분하다.

이 APK는 가중치가 여전히 FP32 약 252 MB이며, K/E만 줄인 workload-lightened 후보다. FP16·INT8 양자화 후보는 정확도 검증이 되지 않았다. 정확한 포터블 실행은 확인했지만 현재 형태를 제품 앱에 연동하지 않는다.

## 범위와 산출물

- 수면일지→39개 특징 생성, 개인화, 권장 시각 계산, UI 전체 지연은 측정에 포함되지 않았다.
- APK 권한 덤프에는 패키지명만 있으며 `INTERNET`을 포함한 요청 권한이 없다.
- 수정 APK: 336,283,891바이트, SHA-256 `17b40499b3ac1621ab3be387f26a8bae903abb17a09e5ac16150f7e2ae753f85`.
- 입력별 벽시계·프로세스 CPU 기록을 추가한 분산 프로브 APK: 336,283,891바이트, SHA-256 `bdfccb7b4bb44ef66867b022e22d156c3f627c2baa24c020baeed64d94569160`.
- manifest SHA-256: `a9f899025307c75c70f45dbfd6404bd27489287bf211a2cdc698d33b6472b324`.
- Android 기준값 SHA-256: `89fdbadbbe524bfeb9176922c747b16a15f1fb8230dd9c12c5820214e0100088`.
- 모델과 Train 컨텍스트가 포함된 연구용 디버그 APK이며 제품 앱에 적용하거나 배포하지 않았다.

초기 오류 그래프의 A52s 전체 실행은 `a52s_full32_doze_contaminated.json`에 진단용으로만 보존했다. 해당 파일은 모델 성능이나 채택 판단에 사용하지 않는다.
